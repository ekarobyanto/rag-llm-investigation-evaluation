**Starting point:** inspect the current repository and reconcile it with [PR #5 and its ID v3 dataset](https://github.com/ekarobyanto/rag-llm-investigation-evaluation/pull/5). Record the actual base commit. The file paths below were verified on `feat/benchmark-id-v3`.

## 2. Align the experiment with Chapter III

1. **Dataset and controls.** Use the matched Indonesian ID v3 corpus and scenarios for the final run. Record their hashes and validate the case title, 150 unique evidence entries, 30 questions, nonempty answers, and valid per-question indices. Use the same model, prompt, corpus, question and retrieval budget across methods. Keep gold answers, evidence labels, difficulty and case solution out of the generator prompt and out of retrieval configuration. Difficulty remains descriptive. Document the PostgreSQL text-search configuration used for this Indonesian corpus, and ensure index and query use the same configuration.
2. **Ranking.** In `lib/rag.ts` and `lib/retrieval/`, remove the benchmark's gold-label-dependent retrieval limit. Return up to ten unique, ordered evidence IDs per question. Feed that top ten to generation and evaluate its prefixes at 5 and 10. Sparse uses PostgreSQL FTS, Dense uses embedding similarity, and Hybrid uses equal-weight reciprocal rank fusion. For ID v3, retain the existing fusion constant 60, sum `1/(60+rank)` across lists in which the document occurs, and remove the custom agreement bonus. Use one-based ranks and deterministic tie-breaking. Record candidate depth and distinguish it from the ten contexts sent to the model.
3. **Retrieval metrics.** Let H be the number of distinct gold IDs in the top K and R the distinct per-question reference set. Use Precision@K = H/K (unfilled positions count as misses), Recall@K = H/|R|, and Hit@K = 1 if H > 0, else 0. Label the aggregate as Hit Rate@K. Record returned count to expose short results. A successful empty retrieval scores zero; an empty gold set or retrieval failure is a data/run error. Freeze the reference labels before comparing methods.
4. **RAGAS.** Use one canonical, version-pinned pipeline and the same judge across methods. Evaluate Context Precision, Context Recall, Faithfulness and Answer Relevancy. Give the evaluator the actual question, answer, ordered contexts and reference answer as required by each metric. Remove the custom Answer Relevancy monkeypatch from the final scoring path. Identify any secondary diagnostic evaluator separately so its scores cannot enter the primary report.
5. **Timing and runs.** Report retrieval latency, LLM generation latency and total response time. Document timing boundaries and units. Track retrieval plus generation consistently across methods and evaluate RAGAS offline. Record dataset version, method, question, repetition, model settings actually sent, prompt version, timestamps, failed/fallback status and retry lineage. For a completed final experiment, expect 30 questions × 3 methods × 3 repetitions = 270 unique successful observations. Report failed attempts separately and summarize by method with variability across repetitions. Repeated runs share the same 30 questions.
